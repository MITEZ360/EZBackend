# 决策日志（Lightweight ADR）

> 记录「为什么这样设计」而非「做了什么」。功能清单与用法见 [README](../README.md)，
> 实现细节见各功能文档。新增重要取舍时追加一条，编号递增，不修改历史条目。

格式：**编号 / 日期 / 状态 / 背景 → 决定 → 后果（含代价）**。

---

## #1　2026-11-02　核心能力走 main，业务衍生功能开分支

- **背景**：项目既要沉淀可复用的通用后台能力，又要尝试资讯聚合这类业务功能；两者混在同一分支会让主线不稳定。
- **决定**：通用能力（认证、RBAC、API Key、会员、迁移、备份、OAuth、文档）直接提交 `main`；业务衍生功能在 `feature/*` 分支开发验证后再合并。
- **后果**：主线始终可发布；资讯聚合在 `feature/news-hub` 完成验证后合入。代价是需要维护分支纪律。

## #2　2026-11-03　运行时零 Node 依赖，前端产物嵌入单二进制

- **背景**：目标交付形态是中小企业可私有化部署的单进程服务，运维不希望额外维护 Node 进程。
- **决定**：前端用 Vue3 + Vite 仅参与构建，`web/dist` 通过 `go:embed all:dist` 打进 Go 二进制；运行时纯 Go。
- **后果**：交付只有一个可执行文件；代价是前端改任何内容都要重新编译 Go 二进制，热更新需另配 CDN 或反向代理。

## #3　2026-11-04　会员到期不删数据，按当前时间实时判定

- **背景**：用户会员到期后，是否被抹成"非会员"？若定时任务改库，会有延迟和状态不一致。
- **决定**：用户表只存等级 ID 与到期时间；是否会员由 `MembershipState()` 按当前时间实时计算；同等级续费顺延、换等级重算。
- **后果**：无定时任务漂移，状态永远准确；代价是每次查询用户状态都要做一次时间比较（成本极低）。

## #4　2026-11-12　API Key 只存 SHA-256 与前缀，签发时回显一次明文

- **背景**：机器身份密钥若明文入库，一旦数据库泄露全部失守。
- **决定**：`ak_s_`（服务端）/ `ak_c_`（客户端）前缀区分类型；库里只存 SHA-256 与前 12 位（用于展示与检索）；明文仅在创建/轮换时回显一次。
- **后果**：DB 泄露不直接暴露可用密钥；代价是用户丢失明文后只能轮换、无法找回。

## #5　2026-11-12　资讯来源与分类改为系统白名单，图标随元数据下发

- **背景**：初版资讯的来源、分类是爬虫自由字符串，脏数据难治理，客户端也不知道有哪些合法分类与图标。
- **决定**：`NewsSource` / `NewsCategory` 由后台预配置（含 `icon/color/sort`）；爬虫推送时未配置来源整批拒绝、非法分类单条标 `invalid` 且批次继续；`category` 必须显式传，不兜底 `general`；开放端 Meta 接口全量下发来源与分类（含图标 URL）。
- **后果**：数据可控、客户端可渲染一致的分类导航；代价是新增分类需先在后台配置。图标 URL 走本地 `/uploads` 静态路由，因此备份必须纳入文件资产（见 #9）。

## #6　2026-11-12　游标分页而非 offset，时间统一 UTC

- **背景**：资讯按时间倒序浏览，offset 分页在持续写入时会重复/漏项；本地时间与 UTC 混用导致排序错乱。
- **决定**：用 `(published_at, id)` 复合游标分页；全链路时间统一 `time.Now().UTC()` 与 `PublishedAt.UTC()`，SQLite 中以格式化字符串比较。
- **后果**：滚动加载稳定不重复；代价是只能单向翻页，不能跳到第 N 页。

## #7　2026-11-13　OAuth 令牌经 URL fragment 回传，而非 query

- **背景**：第三方登录后要把本地 JWT 交回前端。放 query 会被浏览器历史、服务器日志、Referer 记录。
- **决定**：回调后重定向到前端，令牌放在 `#` 之后的 fragment（`#access_token=...&refresh_token=...`），前端 `oauth/callback` 页解析 fragment 写入登录态。
- **后果**：令牌不经服务器、不留日志；代价是需要一个专门的前端回调页来接收。

## #8　2026-11-13　OAuth 绑定表唯一约束用两列组合，冲突返回 409

- **背景**：初版把 `user_id/provider/subject` 三列一起做唯一键，导致同一外部账号可绑多个本地用户；绑定流程查到他人绑定会直接返回该用户，前端提示"已绑定"但关系并未建立。
- **决定**：v4 迁移拆为 `uk_oauth_subject(provider, subject)` 与 `uk_oauth_user_provider(user_id, provider)`；`resolveUser` 在 bind 模式发现外部账号属于他人时返回 409；并发唯一键错误转可读提示。物理清理旧重复行再重建索引。
- **后果**：一个外部账号只能属于一个本地用户，冲突显式报错；代价是追加了一次不可逆的数据清理迁移（`Down` 只能回退结构）。

## #9　2026-11-22　备份产物改为 tar 容器，纳入文件资产

- **背景**：备份只导数据库，但资讯图标、上传附件存于 `uploads/`；恢复后数据库完好、图片全裂（借鉴自外部项目 EZProject 的教训："内容里只有 asset id，DB 备份不含图片字节"）。
- **决定**：备份产物改为 tar 容器，内含 `database.db`、`manifest.json`、`files/`；一次下载/一次恢复拿到完整数据；对象存储模式显式跳过并标注 `storageMode`。保留对旧 `.db/.sql(.gz)` 格式的读取兼容。
- **后果**：恢复后图标可用；代价是备份文件变大、格式升级（旧备份仍可读，新备份需新版本解析）。

## #10　2026-11-22　恢复必须可演练，且永不删最新备份

- **背景**：恢复是高危操作，直接覆盖数据；简单的"保留最近 N 份"在长时间断档后可能把唯一可用备份挤出窗口。
- **决定**：`restore --dry-run` / `?dry_run=true` 只输出计划不改文件，恢复前页面自动演练；恢复后逐表比对行数、报告文件资产还原数；保留策略改为 GFS 分档按槽位挑选，最新一份永不删除，四档全 0 才退回 `retain`。
- **后果**：恢复可预期、可自检，断档不误删；代价是演练与真实恢复共用一套计划逻辑，需保证演练路径绝不写文件。

## #11　2026-11-22　架构约束交给机器：import 边界优先于业务词黑名单

- **背景**：分层依赖铁律（`modules → platform → pkg`）此前只靠人工 Review。外部项目用"内核业务词黑名单"把关，但在 Go 里 `category`、`order` 等是中性词，直接搬会误伤。
- **决定**：`scripts/check_architecture.py` 实现三条贴合 Go 的规则：① platform/pkg 不得 import modules；② 方言判断只在白名单文件；③ `pkg` 导出签名快照变更需 `--update`。纳入 `make verify`。
- **后果**：内核不被业务污染、公共 API 偷改被拦截；代价是新增公共导出或新方言分支时要更新白名单/快照。

## #12　2026-11-22　启动自检关键依赖 fail-fast，非关键只告警

- **背景**：配置错了 Redis 地址但服务"看似正常启动"，多实例状态悄悄分裂；或迁移版本落后却无人察觉。
- **决定**：`bootstrap.New` 装配后探测数据库/缓存/存储（关键项，失败即拒绝启动），迁移版本落后与种子为空只告警；报告挂 `app.SelfCheck`，启动日志打印结论。
- **后果**：问题在启动期暴露而非运行期；代价是启动多了几个探针往返（毫秒级）。

## #13　2026-11-22　跨方言验证必须在真实 MySQL/PG 上跑

- **背景**：某外部项目曾因 5 张表用 `INTEGER` 存 epoch 毫秒在 PG 上完全不可用，而 SQLite（动态类型，`INTEGER` 实为 64 位）侧测试永远发现不了。
- **决定**：`test/dialect_test.go` 用同一套断言覆盖三方言，`make test-dialect` 起临时容器；未设 DSN 时跳过，本地测试不受影响；发版前必须跑一次真库。
- **后果**：方言差异在 CI/发版前暴露；代价是跨方言测试依赖 Docker 且耗时更长，因此不放进日常 `verify`。

## #14　2026-11-22　模块可拔插采用声明式契约，不推翻现有装配

- **背景**：要让模块按配置启停，可彻底重构为注册表驱动的服务定位，但风险高、易让 159 条路由回归。
- **决定**：定义轻量 `Module` 契约（`Name/DependsOn/AlwaysOn`）与注册表，统一 `micro.modules` 与 `modules.enabled`；服务/处理器仍由 `app.go` 统一构造，路由按注册表结果挂载；基础模块常驻、依赖自动补齐、未知模块 fail-fast。
- **后果**：获得按配置裁剪与依赖自检能力，且路由零回归；代价是这不是彻底的服务定位，彻底解耦仍需未来重构（P1-2 已为它留出契约边界）。

## #15　2026-11-25　模块自注册，装配层不再认识具体模块

- **背景**：#14 的声明式契约只做到"按配置开关模块"，加一个模块仍要改 6 处（modulekit 清单、`router.Deps` 字段、`app.go` 构造、`seed.go` 菜单、`module_scope.go` 归属、`router` 挂载分支），裁一个模块也要改同样多地方。这与"基础项目轻量、额外功能按需引入"的目标相悖——目录分了，装配仍是集中的。
- **决定**：① 每个模块一个 `module.go`，`init()` 里 `modulekit.Register` 声明 Name/Label/Desc/DependsOn/AlwaysOn/Models/Menus/Jobs/Setup/Sync；② 装配上下文 `modulekit.Context` 只暴露平台能力与路由分组，模块自己挂路由、注册任务实现、声明启停回调；③ `internal/distribution/default.go` 作为默认发行版清单，只放空白导入，删一行即少一个模块的全部代码；④ 跨模块依赖改由消费方定义小接口 + `Context.After` 注入，模块之间禁止互相 import。
- **后果**：新增/裁剪模块只改一个文件；装配层显著瘦身——`bootstrap/app.go` 599 → 479 行、`internal/router/router.go` 417 → 276 行（零模块 import）、`bootstrap/seed.go` 640 → 365 行、`bootstrap/module_scope.go` 142 → 50 行，11 个 `routes_*.go` 全部删除，声明代码搬进 22 个 `module.go`（合计约 1170 行，属于模块自己的事）。实测裁剪 5 个模块：路由 172 → 126、内置菜单停用 23 条、任务 5 → 3，装配链路零回归。代价是路由顺序由「手写顺序」变成「依赖拓扑序 + 注册序」，需靠路由清单与权限点核对（管理端「路由管理」页）兜底；前端页面仍是全量打包，尚未同构。

## #16　2026-11-25　发行版由生成器组装，备份能力下沉 platform

- **背景**：#15 之后"加模块只改一行导入"，但手工删改导入清单仍不便于按客户组装。同时发现 `bootstrap/cli.go` 为了 `backup` / `restore` 子命令直接 import 了 `modules/maintenance`，导致精简发行版要么缺备份命令、要么被迫带上整个维护模块——装配层仍偷偷绑着一个具体模块。
- **决定**：① `Spec` 增加 `Pkg`，记录模块所属包路径；② 新增 `cmd/distgen`，按给定模块名算依赖闭包（含常驻模块）、翻译成包导入清单，生成带 `profile` 构建标签的 `internal/distribution/profile.go`；`default.go` 为 `!profile`，两者互斥，同一份源码可产出多个发行版；③ `make dist MODULES="…"` / `make dist-list` / `make dist MODULES=all` / `make dist-default` 作为操作入口；④ 备份恢复从 `modules/maintenance` 移到 `internal/platform/backup`，CLI 与运维模块都依赖它，任发行版都有备份能力。
- **后果**：`make dist MODULES="user configcenter cluster"` 产出 10 模块 / 88 路由的精简二进制，被裁接口全 404，装配层零模块 import（`grep internal/modules` 在 bootstrap/router/platform/middleware 下无结果）。代价是包级裁剪的粒度受包结构约束——同包多模块（`system` 包的 dict/config/notice）会整体带进来，模块级差异交给 `modules.enabled`；二进制体积减少有限（约 1MB），因为前端产物全量内嵌，真正瘦身需前端同构。

## #17　2026-11-25　资讯中心移出默认发行版，成为可选模块

- **背景**：#15/#16 解决了"加模块只改一行导入"，但默认清单仍把资讯中心这类演示业务和通用后台混在一起交付——每个项目都白拿一套资讯表、菜单、清理任务和配置项，"按需引入"只是说法。
- **决定**：① `news` 从默认清单移除，代码原地保留在 `internal/modules/news`；② 默认清单改名 `default.go`，全量不再固化成源码里的第二个清单，改由 `make dist MODULES=all` 生成；③ 新增 `internal/distribution/catalog`（默认清单 + 可选模块，只被生成器与测试读取），让 `make dist MODULES="user news"` 仍然组装得出来；④ 配置项增加 `Module` 归属，模块不在发行版时整项与空分组一起隐藏；⑤ `news` 依赖补 `job`，并且发行版没有 `job` 时跳过任务补种（首次种子与增量补种两处都判表是否存在），不再让"这套发行版没有调度器"升级成启动失败。
- **后果**：默认构建 155 条路由（全量 172），新库不建 `news_*` 表，不补种 `news.cleanup`，配置中心没有资讯分组，模块候选清单里也没有 `news`；`make dist MODULES="user news"` 产出 11 模块 / 115 路由的带资讯系统，三张表、清理任务、管理端与开放接口齐全。代价是可选模块要在 catalog 再登记一次（空白导入 + `Optional` 名单），开发者需要判断一个模块属于"通用能力"还是"行业模块"；前端页面仍随骨架打包，菜单进不去、直接访问落 403，同构仍是下一步。

## #18　2026-11-25　国内能力以可选模块并入 main，废弃 main-cn 分支

- **背景**：`main-cn` 平行分支承接国内短信、支付与会员充值，基线停在 `f2873ac`，落后 main 一个提交；此后每个通用改动都要双向合并，分支迟早失同步。而 #15/#16 已让"模块 + 生成器"能表达发行版差异，再用分支表达已无必要。
- **决定**：① 新增两个可选模块：`cnauth`（手机号注册、短信登录、找回密码，依赖 `auth`）与 `recharge`（等级售价、下单、微信/支付宝回调、订单管理，依赖 `membership`），各自 `module.go` 自注册，默认发行版不导入；② 短信 `platform/sms` 与支付 `platform/pay` 留在平台层，仅作为被模块引用的库；③ 微信/QQ 的 OAuth 协议适配留在 `auth` 内部，由 `oauth.providers[].protocol` 驱动，不填即标准 OAuth2；④ 会员 `price` 列由迁移 v9 追加，`cn_sms_code`/`cn_recharge_order`/`cn_payment_config` 三张表交给 `Spec.Models` 在装配时建；⑤ 支付渠道凭据在「充值订单 → 支付配置」维护（加密入库、保存即生效），配置中心只放 `payment.enabled` 总开关与注册/短信参数；⑥ 删除 `main-cn`。
- **后果**：默认发行版零国内代码——注册接口 404、新库无 `cn_*` 表、配置中心无「注册与短信」「支付」分组、模块候选里没有这两个名字；`make dist MODULES="user configcenter cnauth recharge"` 产出完整国内版，实测注册全流程（发码→注册→拿到令牌）与充值接口 200。代价：`cnauth → auth`、`recharge → membership` 是模块间单向 import（架构检查只禁 platform/pkg 反向依赖模块，方向无环，依赖已在 `DependsOn` 显式声明）；顺带修了继承来的缺陷——发码只看 `sms_login_enabled`，只开注册不开短信登录时注册会卡在发码，现按 scene 拆分开关。

## #19　2026-11-25　前端页面按模块自包含，裁剪清单与后端同源

- **背景**：#15~#18 让后端的模块化形成了闭环——加模块只改一个目录加一行导入，`make dist MODULES=…` 能把模块连代码一起裁掉。前端没跟上：20 多个页面全堆在 `web/src/pages/`，路由写死在 `router/index.ts`，裁剪只有 base / full 两档。结果是任何中间组合都是"后端没接口、前端还有页面"，而且加一个模块要改路由表、`api/`、`i18n/locales/partials/`、`pages/` 四处，漏一处就是 404 或缺英文。
- **决定**：① 页面搬到 `web/src/modules/<name>/`，模块名等于后端 `modulekit.Spec.Name`；② 模块默认导出 `WebModule`（`name` / `routes` / `publicRoutes` / `i18n`），`registry.ts` 用 `import.meta.glob` 自动发现，`router/index.ts` 只保留应用壳与全局守卫；③ 裁剪清单由 `cmd/distgen -print` 算出后端实际装配集合（含依赖补齐与常驻模块），Makefile 经 `FRONT_MODULES` 传给 `VITE_MODULES`；④ `web/plugins/module-filter.ts` 在 `load` 阶段把未启用模块的 `index.ts` 换成空模块，使其页面 chunk 真的不进产物，而不是靠运行期开关隐藏入口。
- **后果**：加模块只改模块目录，`router/index.ts`、`i18n/index.ts`、`vite.config.ts` 都不用动；`make dist MODULES="dashboard user role …"` 的产物里 `news`/`recharge`/`apikey`/`cluster`/`workflow` 的页面 chunk 实测全部消失。代价有三：① 模块名与后端不一致时只在运行时表现为 404，靠 `distgen -list` 与文档约定兜底；② 共享接口封装（如 `api/membership.ts`，390 字节，被布局、个人中心、用户页引用）不随模块裁剪，横切引用无法被静态消除；③ i18n 的 key 是全局共享空间，同一句中文不能有两个译法，模块词条只覆盖自己独有的文案，通用词仍集中在 `locales/`。

## #20　2026-11-26　治理面全自研，revision 双轨 + 内存快照

- **背景**：集群管理、服务发现、动态路由、配置中心四件事都只有半成品：节点靠 DB 心跳但 SQLite 下被 `UseCluster()` 直接禁用；网关路由写死在 yaml，改一条要重启；`routemanage` 只是把 gin 编译期路由列出来；`configcenter` 是运行参数在线编辑，没有命名空间、版本、灰度。同时要求不引入 Nacos/Consul/Etcd/Apollo。
- **决定**：① 全部自研，DB 是唯一真相源，外部注册中心与配置中心一律不接；② revision 双轨——全局号判断"要不要拉"，分区号判断"拉哪块"，事务内单调递增，回滚也是产生新 revision，永不回退版本号；③ 数据面只持 `atomic.Pointer[Snapshot]`，读路径无锁无分配，切换靠换指针；④ 刷新三入口（SSE 变更信号、版本轮询兜底、管理端手动下发）统一收敛到幂等的 `Apply(rev)`，SSE 只发信号不发 payload；⑤ 路由规则用强类型表而不是塞进 KV 配置中心，控制面预编译成有序匹配表，数据面只执行；⑥ 网关坚持不连 DB，控制面 HTTP 是唯一通道，启动按"本地快照 → 控制面 → static endpoints"三级降级；⑦ 拆成 `registry` / `route` / `configcenter` / `cluster` 四个模块，运行时能力放 `pkg/gov`，`distgen` 可单独组装成程序。
- **后果**：单实例到 100+ 实例共用一套代码，只调轮询间隔、心跳批量、合并窗口等参数；改一条路由 5s 内生效且零 5xx；控制面停机时网关转发与重启都不受影响。代价：控制面是变更单点（数据面不受影响，但改不了配置）；SQLite 只适合小集群，上量必须换 MySQL/PG；SSE 受文件描述符限制，千级实例要分片；健康检查探针没有现成生态，HTTP/TCP 自研；`routemanage` 与 `configcenter` 需重写，`cluster` 的 SQLite 禁用限制要取消。

## #21　2026-11-26　治理实体走物理删除，保留唯一索引的真实语义

- **背景**：`gov_service.name`、`gov_config_namespace.namespace`、`gov_instance(service_id, instance_id)`、`gov_config_item(namespace, key)` 都是唯一索引，而模型继承的 `Base` 是软删除。软删之后墓碑仍占着索引槽位，同名服务/命名空间再也建不回来——实测删掉 `uitest` 命名空间后重建直接 409。
- **决定**：这四张表的删除一律 `Unscoped()` 物理删除；发布记录与指令记录保持软删除（它们没有唯一业务键，且需要留痕）。
- **后果**：删除即不可恢复，但删除动作本来就会写入审计日志，可追溯性没有损失；重建同名对象不再被历史数据挡住。

## #22　2026-11-26　数据面自注册，版本随心跳收敛

- **背景**：控制面停机不影响转发，但数据面对控制面是"只读消费者"时，页面上看不到网关这个实例，也看不出哪个网关还停在旧版本。`/internal/gov/ack` 存在却没人调。
- **决定**：`pkg/gov.Client` 增加可选的 `Announce`：启动即调 `/api/v1/gov/instances/register` 建档，之后按间隔心跳；每次应用快照后异步上报一次，把观测延迟从"一个心跳周期"压到秒级。实例标识取 `host:port` 而不是 `hostname-pid`，跨重启保持稳定；服务名取显式配置 `gov.service_name`（默认 `tenon-gateway`），不用 `app.name`——那是给人看的显示名，可能含中文。
- **后果**：网关出现在服务目录里，`configVersion` 直接反映收敛进度，"待同步实例"成为可信指标。代价是数据面多两个周期性 HTTP 请求，且首次启动若控制面未就绪会打一条 Warn 并在下个心跳重试。

## #23　2026-11-26　自定义校验器必须复刻 Gin 的切片展开

- **背景**：`httpx` 用带翻译的 `validatorWrapper` 替换了 `binding.Validator`，但它只对结构体调用 `validator.Struct`。Gin 默认校验器会先剥指针、再对切片逐元素校验；缺了这段，任何"请求体是数组"的接口都会拿到 `InvalidValidationError` 并统一返回"请求参数格式错误"——路由规则的编译预览接口就这样稳定失败。
- **决定**：`ValidateStruct` 复刻 Gin 默认实现的分派逻辑（指针剥一层、结构体交给 validator、切片/数组逐元素累计 `SliceValidationError`、其它类型视为无需校验）。
- **后果**：数组请求体恢复正常；将来再加数组型接口不会踩同一个坑。

## #24　2026-11-26　治理面单列发行版，控制面身份由配置决定

- **背景**：治理三件套原先只作为主程序里的模块存在。但运维场景需要一架"只跑治理"的进程：业务系统可能根本不装这套代码，治理台却要独立部署、独立升级、独立备份；混在主程序里意味着治理故障与业务发布互相牵制。
- **决定**：新增 `make dist-gov`（`bin/tenon-gov`），模块集 = Base 的后台能力 + `registry` + `route` + `configcenter`，去掉 `routemanage`（静态路由清单与动态路由语义重复）。前端同源裁剪（`VITE_EDITION=gov`），不靠运行时开关——被裁模块的路由注册代码不在二进制里。同时把控制面自注册的服务名从硬编码 `tenon-core` 改为 `gov.self_service`（默认 `tenon-core`，治理版配 `tenon-gov`）：控制面身份是部署事实，不该写死在代码里。
- **后果**：一套源码产出默认版 / Base / 治理面三个发行版，模块依赖与菜单由 modulekit 闭包统一推导，不需要维护第二份装配代码。治理面自带独立库与端口（9020 / `data/tenon-gov.db`），与被治理系统分库。代价是每加一个治理模块必须同时更新 `GOV_MODULES`，否则该模块不会进治理面二进制——这是编译期裁剪的固有成本，由 `make dist-gov` 的启动日志（模块数 / 路由数）兜底核对。

## #25　2026-11-26　快照去重改用内容指纹，全局版本号退回观测口径

- **背景**：#20 把"要不要拉"的判据定成了全局 revision。端到端测试暴露出两个塌陷：① 注册新实例只清快照缓存、不分配新版本，数据面拿着同一个版本号轮询，控制面一直回 304——扩容后的机器一台流量都不接；② 未发布任何东西时 `rev()` 出于"版本号不能是 0"的直觉做了 ≥1 的下限，于是首版发布拿到的 1 与"还没发布"的 1 撞车，数据面认为首版已经应用过。两者都表现为"控制面看起来正常、数据面永远停在旧视图"。更深一层，registry 分区的在线实例是 `last_seen >= now-90s` 过滤出来的，实例静默下线不需要任何写操作，版本号根本无法表达这种变化。
- **决定**：① `Snapshot.Fingerprint()` 对"分区键 + 分区校验和"排序后取 SHA-256，数据面持有已应用指纹，请求带 `?fp=`，控制面算出一样才回 304；② 版本号不再参与去重，只用于"哪些实例落后"的观测与心跳回报；③ `rev()` 去掉 ≥1 下限，未发布时如实返回 0，分配器从 1 开始，首版发布必然推进；④ `Apply(rev)` 拆成 `Sync()`（带指纹，内容变了才应用）与 `Reload()`（不带指纹，强制全量），SSE 与轮询共用 `Sync`。
- **后果**：扩容、缩容、实例超时下线都能在一次轮询周期内反映到数据面，无需任何发布；无关域发布导致版本号上涨时不再引发全量重建。代价是 304 的判据从"比一个整数"变成"服务端重建快照并算指纹"，控制面每次轮询仍要构建快照（本来就有 1s 缓存）；指纹覆盖内容而非版本号，因此"原样重发一份路由"在数据面看来没有变化——这是期望行为。

## #26　2026-11-27　治理面写路径从严校验，并发冲突按业务语义返回

- **背景**：补极端场景测试时，一批"能存进去但用不了"的输入被翻了出来：端口 70000 能注册成功并原样下发，网关每次转发都拨号失败而服务目录看着健康；路由前缀允许空格与 `?`，写进去永远匹配不上；`status: published` 可以直接创建，页面显示已发布但发布记录里没有它，网关也不转发；配置项批量保存逐条 upsert，第 3 条校验失败时前两条已经落库，调用方收到 400 却以为没改。并发侧则是典型的 TOCTOU：同名服务/命名空间并发创建，输的那一方把唯一索引错误抛成 500；首次扩容时多个实例同时"查不到服务就建档"，撞索引直接注册失败——恰恰在最不该失败的时刻。
- **决定**：① 服务名、命名空间、`gov.service_name`/`gov.self_service` 统一按标识符校验（≤64，`A-Za-z0-9._-`）；实例 `port` 1~65535、`host` 无空白/斜杠、`weight` 0~10000；路由前缀补 `/`、折叠连续斜杠、禁止空白与 `?`/`#`/反斜杠、长度 ≤200；路由 `status` 入参只接受 `draft`/`archived`，`published` 只由发布动作产生；配置项 `key` ≤128、`value` ≤64 KiB、`scope` 只接受 `global`/`service`。② 同名创建在唯一索引冲突后回查，返回 409 而不是 500；注册自动建档撞索引后回查继续，保持幂等。③ 配置项批量保存包进一个事务，整体成功或整体失败。④ 快照 `Build` 的一秒缓存加"代际"戳，`Bump` 递增代际，慢构建不得用旧代际回填——否则发布后整整一秒数据面拿的还是旧视图，且只持续一秒、几乎无法复现。⑤ 请求体超限在中间件按 `Content-Length` 直接 413（业务码 41300），不再依赖解码中途的 `unexpected EOF`（它与"JSON 没写完"无法区分，最终会被报成 400）。⑥ `Config.Validate` 增加 `micro.mode`、`server.mode`、`log.level`、`app.timezone`、`gov.control_url`、`gov.poll_interval` 的启动期校验。
- **后果**：错误输入在入口就被拒绝，错误信息能指出具体字段；并发创建/注册不再产生 5xx；批量保存具备原子性；发布后的旧视图窗口被消除。代价是若干此前"能用"的宽松输入现在会失败（例如中文服务名、带空格的前缀、`poll_interval` < 100ms），需要按新规则调整配置与调用方；`gov.poll_interval` 写裸数字（被解析成纳秒）由启动校验兜住。
